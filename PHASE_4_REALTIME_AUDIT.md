## Executive Summary

Phase 4 addresses Ghostline's dependency on **Supabase Realtime** for database-backed realtime communication.

In Phase 2.5, we proved that when the application repository driver switches to **Neon PostgreSQL** (`DATA_REPOSITORY_DRIVER=neon`), the application writes directly to Neon. However, Supabase Realtime's `postgres_changes` engine watches only the PostgreSQL Write-Ahead Log (WAL) of the **Supabase-hosted database**. Consequently, events generated by Neon writes are never broadcast to Supabase Realtime channels, breaking live message delivery, read receipts, reactions, pins, and inbox notifications.

This audit catalogs every realtime producer, consumer, channel, and event in Ghostline, and defines the target **Ghostline Realtime Gateway** architecture.

## 1. Complete Realtime Inventory

Ghostline currently uses **three distinct Realtime transport mechanisms** provided by `@supabase/supabase-js`:
1. **`postgres_changes` (CDC / Database-backed):** Receives row-level mutations directly from PostgreSQL replication.
2. **`broadcast` (In-memory ephemeral bus):** Client-to-client or server-to-client ephemeral JSON messaging.
3. **`presence` (In-memory distributed state):** Tracks online/offline status and keys (user IDs).

## 2. Realtime Producers & Consumers Breakdown

### Producers:
1. **PostgreSQL Database Engine (WAL CDC):**
   - In the Supabase model, the database is the sole producer of all 9 data events (`messages`, `receipts`, `reactions`, `pins`, `hidden`, `friendships`).
   - Mutations executed by HTTP POST server functions write to PostgreSQL, and PostgreSQL triggers Supabase Realtime via internal replication slots.
2. **Client Browser Tab (Direct Broadcast / Presence):**
   - `chats.$conversationId.tsx`: Calls `channel.send({ type: "broadcast", event: "typing" })` and `channel.track()`.
   - `presence-provider.tsx`: Calls `channel.track()` on `presence:ghostline`.
   - `call-provider.tsx`: Calls `signaling.send(targetUserId, event, payload)`.

### Consumers:
1. **`chats.index.tsx` (Inbox View):** Subscribes to user's global inbox channel to refresh conversation order and friend requests.
2. **`chats.$conversationId.tsx` (Chat Room View):** Subscribes to active conversation for messages, reactions, pins, receipts, typing, and room presence.
3. **`presence-provider.tsx` (Root Provider):** Subscribes to `presence:ghostline` to maintain a set of currently online user IDs.
4. **`call-provider.tsx` (Root Provider):** Listens to `calls:signal:${myId}` for incoming audio/video calls.

## 3. Connection Lifecycle, Reconnection & Ordering

### Current Lifecycle:
1. **Connection Init:** Triggered via React `useEffect` when component mounts or `conversationId` / `userId` changes.
2. **Token Authentication:** Automatically handled by Supabase client using stored access token.
3. **Channel Subscription:** `channel.subscribe(status => { if (status === 'SUBSCRIBED') ... })`.
4. **Cleanup:** Handled in `useEffect` cleanup via `supabase.removeChannel(channel)`.

### Reconnection & Reliability Gaps:
- **No Heartbeat Verification:** Supabase client handles WebSocket ping/pong internally, but if the connection drops silently, React Query does not auto-refetch until user interaction occurs.
- **Out-of-Order Delivery:** Network latency or brief disconnections can cause message events to arrive out of order. Fortunately, the client always sorts messages deterministically by `(created_at, id)`.
- **Missed Events during Disconnect:** If a user closes the lid or loses WiFi, any events broadcast during the disconnected window are lost permanently. Currently, Ghostline recovers only when the user reloads or navigates between routes.

## 4. Existing Optimistic UI & Race Conditions

Ghostline has a robust optimistic update flow in `chats.$conversationId.tsx`:
1. **User Types Message & Clicks Send:**
   - Client generates a local `client_id = crypto.randomUUID()`.
   - Appends temporary message object with `{ id: client_id, pending: true }` to React state.
   - Triggers `doSend({ conversation_id, body, client_id })`.
2. **Server Function `sendMessage`:**
   - Validates authorization (`ConversationPolicy.requireMembership`).
   - Inserts row into PostgreSQL with `client_id`.
   - Returns real row `{ id: "msg-uuid", ... }`.
3. **Realtime Broadcast Arrival:**
   - The recipient's client receives the insert event and calls `qc.invalidateQueries({ queryKey: ["messages", conversationId] })`.
   - The sender replaces the pending optimistic message when the mutation completes.
4. **Idempotency Guard:**
   - PostgreSQL has a unique partial index `messages_client_dedupe_idx (conversation_id, sender_id, client_id) WHERE client_id IS NOT NULL`. Network retry duplicates return the existing message without creating twins.

## 5. Security & Authorization Boundary in Realtime

Under the current Supabase Realtime system:
- **`postgres_changes` channels are authorized by Supabase RLS**: Supabase Realtime queries the database using the user's JWT to decide whether a user is allowed to receive a CDC row event.
- **Broadcast channels are UNAUTHORIZED in Supabase by default**: Anyone subscribed to `chat:conv:${conversationId}` could receive broadcast events if they knew the UUID.

### Mandatory Phase 4 Security Architecture:
In the new **Ghostline Realtime Gateway**:
1. **Authenticated Connection:** Every WebSocket connection must supply a valid authentication token during the initial HTTP upgrade handshake or in the first `auth` message.
2. **Authorized Subscriptions:** When a client sends a `subscribe` frame for a `conversationId`, the gateway must verify that `userId` is a valid member of `conversation_members`. Unauthorized subscription attempts must be rejected with an `unauthorized` error frame.
3. **Producer-Side Publication:** Realtime events for database mutations must **never be published directly from the client**. They must be emitted by the **Server Function** immediately after the database transaction commits successfully:
   ```
   Server Function (POST /sendMessage)
     ↓
   Authorize (ConversationPolicy)
     ↓
   Write to Database (Neon / Supabase)
     ↓
   Commit
     ↓
   Emit to Realtime Gateway: `realtimeGateway.publish("conv:123", { type: "message.created", ... })`
     ↓
   Gateway broadcasts to authorized connected clients in "conv:123"
   ```

## 6. Phase 4 Gateway & Protocol Design

### Target Architecture
```
Browser Client (WebSocketClient)
         │  (Authenticated WebSocket connection)
         ▼
┌────────────────────────────────────────────────────────┐
│             Ghostline Realtime Gateway                 │
│  - Token Verification (Supabase Auth JWT)              │
│  - Connection Registry (userId -> Set<WebSocket>)      │
│  - Room Subscriptions (room:convId -> Set<userId>)     │
│  - Subscription Authorization (ConversationPolicy)     │
│  - Presence & Typing In-Memory State                   │
└────────────────────────────────────────────────────────┘
         ▲                                ▲
         │ (Internal Event Bus)           │ (HTTP / Server Fn Trigger)
         │                                │
Application Services              TanStack Start Server Functions
(MessageService, etc.)            (sendMessage, editMessage, etc.)
```

### Event Contracts

All events emitted over the WebSocket will follow strict, typed domain contracts:

```ts
export type RealtimeEvent =
  // Messaging events
  | { type: "message.created"; conversation_id: string; message: Message }
  | { type: "message.updated"; conversation_id: string; message: Message }
  | { type: "message.deleted"; conversation_id: string; message_id: string }
  | { type: "message.hidden"; conversation_id: string; message_id: string; user_id: string }
  // Engagement events
  | { type: "receipt.updated"; conversation_id: string; message_id: string; user_id: string; read_at: string }
  | { type: "reaction.updated"; conversation_id: string; message_id: string }
  | { type: "pin.updated"; conversation_id: string }
  // Ephemeral events
  | { type: "typing"; conversation_id: string; user_id: string }
  | { type: "presence.sync"; conversation_id?: string; online_ids: string[] }
  // Inbox / Friendship events
  | { type: "inbox.updated"; user_id: string; conversation_id: string }
  | { type: "friendship.updated"; user_id: string };
```
